## 1. Abstract and product hypothesis

A personal agent becomes useful through repeated interaction, but a correction is only valuable if it becomes the right scoped state, governs later actions, survives restarts/upgrades and remains explainable and reversible. Local Nancy/Nanobot and Abi/Hermes records exposed recurring costs around route preservation, delivery truth, compatibility patches and competing state owners. Public issues identify related failure classes, while also showing that upstream projects are actively addressing them. They do not establish market size or comparative defect rates.

Keli's thesis is to make **teaching and approved autonomy dependable across the whole useful agent capability surface**. It should become exceptionally good at scoped correction → enforced behavior → verified outcome → durable recovery, without continually spending tokens reconstructing authority. Native Bun is a means to own that small control path, not the differentiation itself. Browser, web/search/HTTP, shell/files, MCP, skills, memory, jobs, coding delegates, Discord/Telegram and model/auth integrations remain in the product contract. Success must be measured by PRD acceptance and user outcomes, not authored line count.

The architecture was not predetermined. A supported Nanobot foundation was initially attractive. E1 rejected its tested authority seams. A Bun authority core with a Nanobot proposal child then worked, but a matched native Bun slice made the extra runtime unnecessary for that role. An independent OS probe showed filesystem enforcement before Rust was introduced. The resulting decision is one Bun authority/model loop, lazy context and schemas, OS boundaries, optional narrow Rust, and ADOPT → ADAPT → BUILD for capabilities.

## 3. Nancy/Nanobot and Abi/Hermes lessons

The local audit identified Nancy's active Nanobot gateway and distinguished it from the older Hermes deployment. Six installed Nanobot modules were compared with the adjacent checkout: cron service, bus queue and subagent matched; context, memory and skills differed. That establishes version drift, not that each difference was a bug or that the adjacent checkout represented the running image. A release manifest, loaded adapter and service ownership must be part of reproduction. [Discovery §4 and L1/L3](docs/evidence/DISCOVERY.md)

Nancy's startup injection patched `AgentLoop.__init__` and replaced a search tool; the Discord overlay patched a private message handler. These solved real problems but made private signatures into upgrade obligations. The search repair used an isolated bounded process and watchdog; the watchdog is recovery, not resource containment. Reuse the regression expectations and supported integration patterns, not the startup overlay. The native runtime decision removes dependence on those particular seams but does not remove the need for compatibility tests. [Discovery §5, L5/L6](docs/evidence/DISCOVERY.md)

Abi/Hermes history distinguished work done, enqueue accepted and transport delivered. Origin metadata, stable destination IDs, quiet notification policy, atomic persistence, compare-and-swap revisions and compatibility checks were already useful contracts. One documented budget guard was explicitly advisory because the hook could not prevent requests. This is why Keli distinguishes observability from authoritative pre-dispatch enforcement. Preserve those contracts without copying the entire deployment or its domain applications. [Discovery §5 and local Agent assessment, L2/L4/L13](docs/evidence/DISCOVERY.md)

Historical fixes included Discord route preservation, truthful unconfirmed delivery, staged-versus-active records, and diagnostic ID/user-D-Bus corrections. They support typed state and operator diagnostics. The source record also described migration/import ownership to avoid duplicated live schedules. Keli imports jobs paused and requires destination/grant validation. No controlled replay of all private conversations established a universal cause for forgotten instructions; retrieval, compaction, ambiguity and multiple writers remain distinct hypotheses. [Discovery §5 and L11/L12](docs/evidence/DISCOVERY.md)

## 4. Architecture experiments, including rejected paths

### EXP-E1 — a supported Nanobot foundation

**Hypothesis:** retain Nanobot as the runtime while a small supported SDK extension owns durable behavior and universal pre-execution gates. Unmodified upstream pin was `c4a25c9a0977f5729ffabde0b10f641dae08774d` (package 0.3.0); 323 installed Python modules were verified. The isolated harness used 281 code LOC plus 13 metadata lines and 15 assertions.

**Result:** lifecycle state survived the fixture; explicit strict SDK hooks, including the ephemeral case, worked. Default hook exceptions failed open, factory errors could be suppressed, and native child/MCP retry paths exposed unsupported universal-control assumptions. **NO-GO for foundation A at that pin**, not “Nanobot is insecure everywhere.” Supporting specific hooks is weaker than controlling all entry points and retries. The two-call benchmark (205.21 ms baseline / 179.66 ms behavior) is noisy and establishes no speedup; token figures were estimates. The small stable adaptive-state hypothesis survived; the proposed ownership placement did not. I1/I2/I3 require native enforcement ownership. [Report and raw artifacts](docs/evidence/DISCOVERY.md#l19)

### EXP-B — Bun authority with a Nanobot proposal process

**Hypothesis:** remove upstream authority; let a persistent Python child propose while Bun owns rules, SQLite, action identity, gates and outcome. Three source files totaled 296 lines (120 core, 99 adapter, 77 tests); 22 assertions passed.

**Result:** GO WITH LIMITATION for the narrow owned-control design. Matched direct/child arms each used one provider call. Added warm median was 13.07 ms, approximately 8.4%; measured components included deterministic 11.63 ms and IPC 1.07 ms. Ping median was 0.437 ms, p95 1.252 ms; observed cold cases were 2.121/1.614 seconds. These separately sampled statistics must not be added into an exact latency identity. The child still supplied large context/request overhead. Same-user IPC established a control contract, **not a security boundary**; effect execution was fake. This made native comparison worthwhile without claiming Python could not work. [Report](docs/evidence/DISCOVERY.md#l20)

### EXP-NATIVE — matched native model/proposal slice

**Hypothesis:** a thin Bun adapter can retain the tested one-call proposal role with lower context/process/dependency overhead. It was 29 newly authored adapter lines, not a 29-line complete agent; five source files totaled 300 lines including copied control/comparison code. Thirteen assertions passed. Bun 1.4.0, Python 3.12.3, the same Nanobot pin and the **same Bun-hosted scripted fixture** were used. Twelve warm samples per arm after excluded warmup and three cold samples per arm were recorded.

| Metric | Native Bun | Bun → Python/Nanobot | Interpretation |

| Compact context bytes | 450 | 8,929 | B report's separate serializer gave 9,008; do not conflate representations |

**Result:** NATIVE BUN CLEARLY BETTER for the tested role, supporting DEC-ARCH-01. The 35 active direct Nanobot requirements are a different count from installed distributions. The native adapter rejected malformed/non-final/tool-call candidate responses; it was not a production tool loop or broad provider SDK. No live-model quality, cache economics, long-task success, full feature parity or end-to-end security was measured. All 15 B manifest files were verified unchanged. Retain the one-loop/lazy-schema philosophy and build proper supported integrations, not blind ports. [Report](docs/evidence/REPORT.md)

### EXP-OS — OS-first probe and optional Rust broker

**Hypothesis:** a small Rust broker is needed to make execution restrictions real. First an independent Python OS probe ran; then the Rust controller/broker reproduced the boundary. On Linux 6.8.0-138-generic with Landlock ABI 4, forbidden synthetic outside-file reads/writes and symlink escape failed. A negative broker test skipped the application path check and was still denied by the kernel. `no_new_privs` and filesystem rights 0–14 were used. Bubblewrap was absent and user namespaces were denied on this host.

The Rust 1.98.1 std-only prototype totaled 176 lines (broker 90, controller 48, probe 38) and 14 assertions. Process-group timeout was set to 30 ms and observed at 38.908 ms with kill/reap; restart passed. Two hundred pings gave median 0.212 ms and p95 0.937 ms, excluding child spawn/confinement/effect costs. This is not a cross-language throughput benchmark.

**Result:** RUST OPTIONAL / OS PRIMITIVES SUFFICIENT for the demonstrated filesystem slice. Rust raw syscalls were host-specific; a language choice was not the enforcement mechanism. No network containment, macOS backend, compromised-controller defense, general descendant escape resistance or CPU/memory envelope was established. Keli must validate those supported execution paths during implementation; fail closed when unavailable. Landlock alone is not the entire sandbox. [Report](docs/evidence/REPORT.md); [combined closure](docs/evidence/REPORT.md)

### What changed, and what did not

Rejected: foundational Nanobot at the tested seams; mandatory Python proposal runtime for the narrow model role; default Rust Guardian; broad unrestricted writable host access described as safely interceptable by a model gate. Modified: stable core/adaptive state survives, but the core owns execution truth rather than layering advisory hooks over another owner. Kept: reuse before rewrite, broad capabilities, personal-first design and efficient context. Not tested: market adoption, superiority to every other agent, live intelligence, cross-platform production containment. Those are not silently upgraded to facts by the owner architecture decision.

## 6. Reuse and current repository lessons

**ADOPT → ADAPT → BUILD** is a per-capability workflow, not an excuse to postpone capabilities. Inspect the current upstream implementation at a pin, select the maintained library/protocol where possible, adapt the thin integration or UX contract, and build only the Keli-specific ownership/enforcement. Record pin, license/notices, what changed, why a dependency was rejected, I/A trace and conformance tests. No automatic whole-project Python-to-TypeScript translation.

| Capability | Inspect first / reuse direction | Keli-owned behavior |
|---|---|---|
| Browser/web/search/HTTP | Nanobot web tools; Hermes browser/search/session patterns; maintained Playwright and provider clients | Readiness, scope, bounded output, credential/cookie ownership and side-effect truth |
| MCP | Both runtimes' connections/discovery/lifecycle; maintained TypeScript protocol client | Lazy schemas, grants, lifetime and disposal |
| Shell/files | Backend/resource/path/cancellation patterns in both; OS primitives | Authoritative dispatch and tested mediated execution, no duplicate shell implementation |
| Skills/memory | Nanobot lightweight skill/context loaders; Hermes skill workflow and Tool Search/local memory | Typed state, dedup, versioning, scope and undo; optional Honcho cannot own rules |
| Jobs/triggers | Cron/heartbeat lifecycle and quiet-output patterns | Deterministic zero-call waiting, durable occurrence/delivery truth |
| Delegates | ACP/external-process patterns; each coding CLI's real lifecycle | User choice, supervision/fencing and verification |
| Discord/Telegram | Thread/topic/rendering/pairing patterns; maintained platform libraries | Durable origin, authentication, exact grants and independent delivery |
| Providers/auth/onboarding | Supported SDK/protocol and Hermes connection/doctor UX patterns | Primary/fallback policy, masked setup, small context, typed errors and exact usage |

The final **remote** audit pinned Nanobot `aeb7b207d7e501b1dd5d8b68208813f493411331` and Hermes `05d705dd695d1084388529124dc2ffe5ce919e89`; these are different from the E1/native test pin. It found useful governance and packaging patterns: Nanobot's Bun TUI build/hash code; Hermes's explicit OS trust-model, dependency-path review and install tests. Adopt the patterns that fit; do not copy Nanobot's no-macOS-CI cost policy or Hermes's multi-runtime/layout complexity. Public rulesets were inspected; private reporting/scanning settings not publicly verifiable remain unknown. Full per-practice findings, pinned links, proposed files and G01–G05 checks are in [REPO_GOVERNANCE.md §2](REPO_GOVERNANCE.md).

## 7. Delivery evidence and outstanding validation

Bun-first tooling is DEC-TOOLING-01: one package manager/lock, test runner, build/compile pipeline and repo-owned TypeScript scripts, with small CI wrappers. Current Bun documentation supports the four Linux/macOS compile targets. The experiments used 1.4.0; documentation advertises 1.4.2, which is a planned pin pending implementation compatibility tests. `Bun.secrets` is experimental and Linux requires secret-service infrastructure; one executable does not remove external browser/delegate dependencies. The plan explicitly separates local, CI, release and installation/update automation, and uses TypeScript checking/platform signing where Bun is insufficient. [Verified APIs and limitations](REPO_GOVERNANCE.md)

Unproved release obligations remain: natural-language correction quality; actual OS/files/network/resource/secret restrictions on both OSes; real delegate cancellation/fenced fallback; recovery from ambiguous external effects; compiled connector/assets behavior; credentials after signed upgrades; durable-state migrations/rollback; and first-user setup usability. These are implementation acceptance work, not a reason to restart architecture discovery or ask the owner the same questions again.

Future research refreshes append dated upstream resolutions, real acceptance evidence and user results. Preserve NO-GO findings and fixture limitations. Do not replace this record with marketing claims, treat lower tokens as inherently better intelligence, or call planned coverage a passed test. Product research exists now; ongoing research maintenance need not block v0.1.0 implementation.
